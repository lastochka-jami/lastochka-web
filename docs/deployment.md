# Развёртывание и откат

Приложение собирается в Next.js standalone и работает под `/shop`. Сетевые адреса, SSH-реквизиты и конфигурация инфраструктуры хранятся вне репозитория.

## Настройки

Для `Deploy web` требуются GitHub Actions secrets:

| Secret | Содержимое |
|---|---|
| `WEB_DEPLOY_HOST` | SSH-хост |
| `WEB_DEPLOY_USER` | Ограниченный пользователь доставки |
| `WEB_DEPLOY_KEY` | Приватный ключ только для forced command `deploy <SHA>` |
| `WEB_KNOWN_HOSTS` | Заранее проверенный ключ SSH-хоста |

На целевой среде отдельно настраиваются Node.js 24, systemd, reverse proxy, runtime env, SQLite и права на каталоги. Переменные приложения перечислены в [`.env.example`](../.env.example). `PUBLIC_ORIGIN` задаётся без `/shop`, ключ сессии — 64 случайных hex-символа. Checkout включается только после проверки платёжного return URL.

## Сборка и доставка

PR проверяет `CI`, без доступа к production secrets. Только ручной запуск из `main` запускает `Deploy web` (push и слияние PR не выполняют доставку): тесты, типы, сборку, упаковку standalone с `public` и `.next/static`, передачу архива по SSH с проверкой host key. Не запускать этот workflow для одной только проверки PR.

Receiver `deploy/receive.py` устанавливается администратором среды отдельно от приложения. Изменение файла в Git не обновляет установленный receiver. Перед применением обновления receiver выполнить его Python-тесты, сохранить предыдущую установленную версию и установить проверенный файл с прежними владельцем и правами. GitHub workflow не имеет административного shell-доступа.

Receiver сериализует выкладки, проверяет архив, переключает ссылку на новый релиз и перезапускает только веб-службу. Затем проверяет ревизию и `/shop/`, `/shop/catalog`, `/shop/search`. При ошибке активации или smoke возвращает предыдущий релиз. Runtime env и данные сессий не входят в архив.

## Хранение релизов и диагностика

Сохраняются текущий и два последних автоматически загруженных релиза. Удаление старых релизов — обслуживание после успешного smoke: ошибка прав на созданный runtime каталог cache выводит предупреждение и не превращает успешную активацию в сбой доставки. Администратор среды должен отдельно исправить права/очистить оставшиеся старые релизы и контролировать свободное место. Не расширять права deploy-пользователя до неограниченного sudo.

При сбое смотреть конкретный шаг в Actions. Успешная сборка не доказывает успешную доставку, а предупреждение очистки не означает откат. Для ручного отката оператор среды переключает ссылку на сохранённый проверенный релиз, перезапускает веб-службу и повторяет smoke. Ключ сессии и SQLite сохраняются. Backend и его база не обновляются этим процессом.

После доставки отдельно проверяются публичные страницы и пользовательские сценарии; smoke receiver не покрывает оформление заказа и оплату.
