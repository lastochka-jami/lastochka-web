# Бонусы и привязка банковских карт

## Источники данных

Баланс берётся из `GET auth/profile` → `bonusBalance`, аналогично мобильному `BonusCubit`. Один `ProfileStore` обслуживает главную, профиль, настройки и экран бонусов. Вход, операции с корзиной и заказами, изменение профиля и возврат к вкладке обновляют его. Временная ошибка сохраняет последний известный баланс. До первого ответа отображается загрузка либо ошибка с повтором; ноль показывается только после ответа с нулевым балансом.

Сессия определяет область личных данных: выход и смена сессии очищают профиль, удаляют совместное использование старых запросов и исключают применение запоздавших ответов. Номер, статус и QR карты независимо загружаются через `GET loyalty-card`; ошибка этой ручки не обнуляет бонусы.

## Привязка и возврат

Последовательность совпадает с мобильной: запрос привязки → защищённая платёжная страница → возврат → серверный список карт. Для браузера сохраняется текущий origin: host-only HttpOnly cookie с `SameSite=Lax` и `Path=/shop` должна вернуться на исходный домен.

`PUBLIC_ORIGIN` и необязательный `SECONDARY_PUBLIC_ORIGIN` задают точные разрешённые origin веба. Прокси отклоняет чужой origin, credentials в URL и пути вне `/shop`. Устаревшая переменная `ALLOWED_PAYMENT_RETURN_URL` больше не меняет домен возврата.

**На стороне API оба домена должны быть разрешены в `YOOKASSA_ALLOWED_RETURN_HOSTS`.** Хост APP_URL и дефолтного адреса возврата также разрешаются серверным `ReturnUrl`. Проверка конфигурации обязательна при подключении дополнительного домена. Переключать боевой магазин YooKassa в тестовый режим для этого не требуется.

Только `errors.returnUrl` означает ошибку адреса. Другие 422 сохраняют сообщение API, например отказ создания платежа.

Перед уходом в `sessionStorage` сохраняются ID пользователя, исходные ID карт и время начала. Токен авторизации туда не переносится. После возврата серия из пяти серверных проверок с паузами по две секунды ищет новую карту; `GET payment-cards` на стороне API сверяет незавершённые привязки со шлюзом. Пока результата нет, отображается ожидание. После лимита доступен ручной повтор. Параметры `binding` и `status` запускают проверку и не доказывают успех.

## Обновление после отмены заказа

`OrderResource` может не возвращать `canCancel`. Веб учитывает допустимые сервером статусы `draft`, `pending`, `assembling` и явный запрет `canCancel:false`. После отмены обновляются заказ и общий профиль. Окончательное разрешение отмены проверяет API.

## Регрессионные проверки

- `tests/profile-binding.test.ts`: ошибка профиля до и после первого ответа, настоящий нулевой баланс, смена аккаунта, выход и поздние ответы; разделение ошибок 422; немедленное и задержанное появление карты; ограничение проверок; оба origin; статусы отмены заказа.
- `tests/client.test.ts`: смена аккаунта исключает совместное использование старого личного запроса.
- `tests/bonuses-cards.e2e.ts`: независимость QR от ошибок профиля, сохранение и смена баланса, отказы API, недоверенный флаг успеха, прекращение опроса и ручной повтор, полный переход через другой origin с настоящей локальной BFF-сессией на основном и дополнительном доменах, отмена заказа без `canCancel` и обновление профиля.
- Проверки профиля и pending-карты используют заведомо отличающийся `loyalty-card.balance`, чтобы обнаружить возврат к прежнему источнику баланса.

```sh
python3 -m unittest discover -s deploy -p 'test_*.py'
npm test
npm run typecheck
npm run build
npx playwright test tests/bonuses-cards.e2e.ts tests/regressions.e2e.ts tests/mobile-audit.e2e.ts tests/shop-mount.e2e.ts --grep 'bonus|account switch|binding|roundtrip|loyalty|profile has|shop pages|phone login|real API order shape'
```

Дополнительно проверены закрытый preview с production API на явно настроенном тестовом клиенте и отдельный API с копией его данных, изолированной БД и настоящим тестовым магазином YooKassa. Проверены `test:true` до ввода тестовых реквизитов, возврат и сохранение сессии, появление карты, снятие тестового холда, отказ API, смена аккаунта и возврат бонусов после реальной отмены подготовленного заказа в копии. Тестовые конфигурации, данные клиентов, токены и отчёты с окружением не входят в репозиторий.

## Ограничения

API не возвращает ID и конечный статус отдельной попытки привязки. По одному списку нельзя однозначно отличить повторную привязку уже сохранённой карты от отмены или большой задержки. Без локального контекста, при возврате в другую вкладку или при превышении лимита веб обновляет список и оставляет результат неподтверждённым.

Браузерные проверки используют Chrome с мобильным и настольным viewport; они не заменяют проверку Safari, физических телефонов, 3DS и переходов в приложение банка. Полный checkout с внешней доставкой и 1С в этот набор не входит. Настоящая служебная карта для боевого банковского smoke вводится сотрудником самостоятельно; тестовые реквизиты YooKassa применимы только к тестовому магазину.
